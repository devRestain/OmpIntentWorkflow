# OMP에 전달할 최종 구현 지시 — v3

이 디렉터리의 자료를 사용하여 나의 로컬 OMP 작업 환경을 구현하라. v1·v2와 충돌하면 이 v3와 이후 내 지시를 따른다. 아래의 사용자 경험과 검증 조건을 실제 동작으로 완성하는 것이 목표다.

## 내가 원하는 작업 경험

새로운 목표를 주면 곧바로 제품 코드를 구현하지 말고, guided-goal처럼 나와 대화하여 원하는 기획을 만든다. 현재 이해한 목표·주요 흐름·제약·완료 기준·중요한 선택을 보여 주고, 내가 원하는 안이 될 때까지 수정한다. 내가 명확하게 그 기획으로 구현을 시작하라고 하면 오케스트레이션으로 실행한다.

실행 중에도 내가 자연어로 질문·수정·중단·재개할 수 있어야 한다. 나의 최신 의도가 관계되는 작업자와 검증·통합 경계에 적시에 전달되어야 한다. 접수됐다는 알림과 실제 결과에 반영됐다는 상태를 구별해 보여 준다.

거대한 계획은 실제 Git linked worktree를 사용해 준비된 독립 작업을 적극 병렬 실행한다. 여러 모델·세션·총토큰 증가를 허용한다. 자원 과다 사용 방지는 새 근거나 결정의 진전이 없는 과추론·반복 검토·무의미한 재시도 억제로 한정한다. 저비용을 이유로 유용한 병렬성을 임의로 제한하지 마라.

## 유지할 세 철학

1. 모호한 자연어를 목표·제약·실행 규칙·검증 가능한 완료 조건으로 자동 강화한다.
2. 다중 모델과 분리된 context를 활용하되 원문·유효한 수정·승인·작업 근거를 보존해 초기 의도의 손실을 막는다.
3. 과추론을 억제한다. 큰 작업의 합리적인 추론·병렬 구현·검증을 토큰 수만으로 줄이지 않는다.

Felix의 철학은 원자료·전문적인 방법·외부 검증을 강화하는 데 적용하라. 더 깊은 방법과 더 큰 미승인 범위를 혼동하지 마라. 내 목표를 넓히는 제안은 기획에서 비교 가능하게 제시한다.

## 0. 먼저 현재 환경과 구체적 기획을 확인하라

설치된 OMP 버전·활성 profile·실제 TypeScript API·설정·extensions·모델·Git 저장소·미커밋 변경·프로젝트 지침을 읽어라. 기존 credential 값을 출력하거나 새 파일에 복제하지 마라. 기존 작업은 보존한다.

README와 DESIGN을 먼저 읽고, 구현할 경계에 필요한 문서만 추가로 읽어라. OMP_CAPABILITIES와 PI_OR_OMP의 main 문서를 설치 release가 전부 지원한다고 가정하지 마라. 2026-11-10 조사에서 확인한 release는 OMP v18.18.6이며, 이것은 설치 환경의 버전이라는 뜻이 아니다.

이 환경을 구현할 구체적인 기획을 짧게 제시하라. 지원 가능한 사용자 입력 경로, 실제 worktree 실행 방식, canonical 상태 위치, 변경 파일, 검증·복구 방법과 미정 사항을 보여 줘라. 나는 필요한 수정을 대화로 할 수 있어야 한다. 내가 그 기획으로 구현을 시작하라고 하면 이미 확정한 범위의 구현·검증·복구 안내까지 진행하고, 계획 문서만 남기고 끝내지 마라.

## 1. 기본 구현 선택

기본은 **OMP를 재사용하는 하나의 응집된 workflow package**다. 의도·승인·작업 배정·steering·통합 규칙은 프레임워크 독립 모듈에 두고 OMP adapter를 연결한다. OMP의 모델 연결·도구·세션·가능한 UI를 재사용한다. 기능마다 독립된 상태를 소유하는 여러 플러그인을 조립하지 않는다.

Native Task가 요구한 실제 linked worktree·입력·취소·통합 경계를 충족하는지 조사하라. `isolated:true`, branch merge mode, 별도 폴더라는 이유로 Git worktree라고 주장하지 마라. 필요하면 `git worktree add`로 만든 cwd마다 OMP SDK/RPC 세션을 실행하는 좁은 worker adapter를 구현한다. OMP core patch가 넓어지거나 자체 실행기가 기존 기능 대부분을 우회하면, 같은 의미 규칙을 pi로 연결하는 대안을 구체적 근거와 함께 제시한다. 두 실행기를 처음부터 전부 구축하지 않는다.

큰 구현 전에 작은 end-to-end 경로를 완성하라: 기획 수정·확정 → 두 실제 worktree → 병렬 실행 → 한쪽에만 steering → 오래된 결과 차단 → 최신 결과 검증·통합 → 재시작 복구. 이 경로가 요구를 충족하는지 확인하고 기능을 확장한다.

## 2. 대화형 기획과 확정

새 작업은 planning 상태에서 시작한다. 목표, 대표 사용자 흐름, 포함·제외 범위, 명시 제약, 필요한 원자료, 중요한 방법 선택, 완료 판단, 남은 결정, 병렬화 구상을 함께 다듬는다.

매번 긴 양식을 강요하지 말고 변경된 부분과 중요한 질문을 먼저 보여 줘라. 코드로 알 수 있는 사실은 조사하고, 결과를 바꾸는 선호와 모호함만 나에게 물어라. 정해진 횟수 때문에 미완성 기획을 확정하지 마라. 읽기와 허용된 기획 실험을 제품 구현의 승인과 구별한다.

확정은 실제 내가 본 draft revision/content와 사용자 이벤트에 결합한다. native plan review가 허용하는 편집 때문에 사전 preview와 실제 승인 내용이 달라질 수 있으므로 최종 snapshot을 확인하라. refine·save·pause·취소·침묵을 승인으로 바꾸지 마라.

“좋아, 결제는 빼고 시작해”처럼 확정과 결정적인 수정이 함께 있으면 그 원문을 근거로 수정된 기획을 기록하고 진행한다. 불명확한 새로운 선택만 질문한다. 기존 승인으로 이후 표시되지 않은 새 기획을 실행하지 마라.

## 3. 원문과 실행 상태

Intent·WorkItem·Result와 작은 이벤트 기록으로 시작한다. 원문, 해석, 관찰, 가정, 방법 제안을 구별하고 요구의 출처를 연결한다. 목표·제약·허가도 구별한다. 정상적인 schema나 source pointer만으로 의미 보존을 증명했다고 하지 마라.

한 run에는 canonical writer가 하나여야 한다. native custom entries 또는 run-local journal 중 하나를 정본으로 삼고, 다른 세션·UI는 참조와 재생성 가능한 view를 가진다. 코드 branch 전환이나 context 압축으로 원래 목표·승인·중간 수정이 사라지지 않아야 한다.

전역 기획 revision과 작업별 영향 epoch/attempt를 분리한다. 전체 기획에 사소한 변경이 생겼다는 이유로 무관한 작업까지 무효화하지 않는다. 요구 version·입력·의존 관계가 유지됐다는 근거가 있으면 이전 전역 revision의 결과도 현재 기준으로 채택할 수 있다.

## 4. 실행 중 자유로운 steering

주 세션의 긴 추론이나 모든 worker 완료를 기다리지 않는 입력 경로를 구현하라. host가 실제 사용자 입력을 먼저 기록하고 접수 상태를 보여 줘야 한다. 자연어 입력을 질문·수정·추가·pause·resume·cancel·승인으로 구별한다.

입력이 미해석 상태라면 영향이 미확정인 새 변경·통합을 잠시 보류한다. 상태 질문으로 확인하면 즉시 해제하고 기존 작업을 취소하지 않는다. 명확한 수정은 해당 수정 자체를 실행 근거로 사용하고 반복 승인받지 않는다.

관계되는 요구·코드·입출력 계약·의존 작업을 찾아 영향 범위를 갱신한다. 파일이 다르다는 사실만으로 독립이라고 판정하지 마라. 영향받는 작업에 원문·변경 내용·유지 조건·현재 epoch를 보내고 확인을 받는다. 무관한 작업은 계속한다.

수신·영속 기록·대상 판정·전달·worker 확인·실제 반영을 구별한다. 높은 sequence 하나만 받았다고 이전 관련 변경을 모두 확인했다고 추정하지 않는다. 누락 없는 관련 event 집합 또는 처리 cursor를 사용한다. 오래된 attempt의 확인을 새 attempt의 확인으로 인정하지 않는다.

native focused-child 입력이나 RPC 등 주 input hook을 거치지 않는 경로가 있는지 반드시 확인하라. 지원하는 모든 steering 경로는 canonical ingress로 먼저 들어와야 한다. 불가능한 경로를 전체 지원한다고 표시하지 말고, 자연어를 받는 통합 steering UI/명령 또는 host RPC gateway로 보완하라. 가능하면 기존 UI를 재사용하되 전역 의도가 누락되는 경로를 조용히 남기지 마라.

취소 요청·실제 종료·이미 발생한 효과를 구별한다. `steer` 성공이나 abort signal이 비중단 shell/network 요청을 즉시 멈췄다는 뜻이 아니다. 제어할 수 있는 다음 도구 경계와 결과 채택 경계에서 최신 상태를 검사하라. 제어하지 못하는 외부 효과는 그 경로에 맡기지 않는다.

## 5. 실제 worktree 병렬 구현

기획을 의존성과 완료 기준이 있는 WorkItem으로 분해한다. 준비된 독립 작업은 가용 역량까지 실행한다. 모델 추론, 로컬 모델, build/test, 공유 자원, Git 통합의 동시성은 별도로 관리하라. 기존 provider·하드웨어 제약을 확인하되 새 절약 목적의 낮은 전역 한도를 강제하지 않는다.

각 구현 작업은 실제 linked worktree와 고유 branch를 사용한다. `git worktree list --porcelain`, 실제 cwd, HEAD, common-dir, base input을 확인한다. 한 branch를 강제로 여러 worktree에 checkout하지 마라. 작업별 read/write 범위와 인터페이스 계약을 두고 포트·DB·임시 파일·빌드 출력도 분리하거나 독점한다.

사용자 원본의 미커밋 변경을 보존한다. 이번 작업에 필요한 변경은 원본을 건드리지 않는 snapshot/patch manifest에 포함하고, ignored·비밀 파일을 자동 commit하지 않는다. 기준 HEAD만 기록해 실제 입력에서 사용자 변경을 빠뜨리지 마라.

작업자는 자신의 branch에 결과를 남기고 정확한 artifact commit과 검사 증거를 반환한다. native isolation을 함께 쓰면 자동 apply를 꺼서 통합 gate를 우회하지 않게 하라. worker에게 주 브랜치 자동 merge 권한을 나눠주지 않는다.

통합 후보 작성과 검토는 병렬로 해도 된다. 채택할 통합 ref·canonical 결과 상태의 최종 갱신은 단일 writer가 수행한다. 후보 검사 중 새 steering을 받을 수 있어야 하며, 최종 채택 직전에 현재 입력 cursor·관련 요구/epoch·통합 HEAD·검사한 commit을 재확인한다. 무관한 변경은 호환성 근거로 처리하고, 영향 있는 변경이면 다시 검증한다.

Git와 journal을 하나의 원자 transaction으로 가정하지 마라. 준비·실제 ref·채택 상태를 기록하고 중도 장애를 복구하며 같은 patch를 중복 적용하지 않는다. 복구 전에는 변경/통합을 재개하지 않는다. 기존 pause/cancel은 명시적 재개 없이 해제하지 않는다.

## 6. Context와 모델

각 세션에는 현재 목표, 적용되는 원문 제약, 이번 WorkItem, 최신 steering, 필요한 코드·증거, 조회 가능한 원자료 참조를 제공한다. parent 전체 대화를 무조건 복제하지 마라. 원문 지시와 untrusted tool/file 내용을 구분한다.

상위 context에는 완료 결과뿐 아니라 미완료·실패·새 장애물·목표를 바꾸는 관찰도 전달한다. 긴 로그는 조회 가능한 artifact에 둔다. UI 축약과 실제 provider payload 축약을 구별하고 tool call/result 구조를 유지한다.

기획 의미·큰 불확실성에는 충분히 강한 모델을, 정해진 독립 구현에는 실제 수행 성적에 맞는 모델을 사용한다. 모델과 reasoning effort를 별개로 선택하라. local System One과 스킬 classifier는 선택 사항이다. route마다 추가 agent를 호출하거나 모든 작업에 최대 reasoning을 강제하지 않는다.

## 7. 과추론 억제

추가 조사·후보·검토에는 미해결 질문, 그 결과가 바꿀 결정, 종료 조건이 있어야 한다. 같은 실패를 입력·방법·근거 변경 없이 반복하거나 충분한 결과를 계속 재검토하지 마라. 실제 완료 기준을 만족하면 종료한다.

유용한 병렬 세션, 높은 누적 토큰, 긴 필요 추론은 그 자체로 실패가 아니다. 총소비는 관측하되 내가 정하지 않은 작은 비용/호출 상한으로 대형 기획을 끊지 않는다. 기존 명시 한도와 실제 자원 제한을 존중하고 충돌은 보여 줘라. 모든 사용량을 관측하지 못하면 unknown으로 보고한다.

## 8. 완료 검증

reference 코드는 in-memory 개념 모델이다. 그것이 통과했다고 OMP와 Git 통합이 검증됐다고 하지 마라. 실제 구현에서 다음을 확인하라.

1. 기획을 여러 번 수정하고 확정 전에는 제품 구현 worker가 시작되지 않는다.
2. 승인한 내용과 실제 실행 내용이 일치한다. pause/refine/save를 승인으로 취급하지 않는다.
3. 두 개 이상의 실제 linked worktree에서 병렬 실행하며 파일·포트·테스트 자원을 필요한 만큼 분리한다.
4. 실행 중 질문은 답하고, 명확한 수정은 관계되는 worker에 전달해 확인한다. 무관한 worker는 계속한다.
5. 오래된 결과·ack·늦은 completion은 잘못 채택되지 않는다. 관련 변경 누락을 max(sequence)로 숨기지 않는다.
6. 후보 테스트와 steering이 경합해도 최종 채택이 현재 기준을 다시 검사한다.
7. 사용자 pause/cancel·연결 끊김·host 재시작 후 상태와 실제 Git/process를 대조하며 중복 실행·중복 merge를 막는다.
8. 원문 의미를 의도적으로 누락·축소한 명세를 최종 원문 기준 검토가 발견한다.
9. 대표 대형 작업에서 순차 기준과 병렬 경로의 완료 시간·의도 준수·통합 재작업을 비교한다. 총토큰 감소는 성공 요건이 아니다.
10. 재실행 가능 설치, 기존 설정 보존, 비활성화·복구, 사용법을 제공한다.

검증은 실제 위험과 요구를 해결하는 데 필요한 만큼 수행한다. 모든 모델·사례 조합의 대규모 benchmark를 기본 설치의 선행 조건으로 강제하지 않는다. 실행하지 못한 경로는 not_run과 구체적 이유를 적는다.
