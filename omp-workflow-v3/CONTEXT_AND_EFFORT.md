# 컨텍스트, 모델 선택, 과추론 억제

## 1. 컨텍스트를 아끼는 목적

상위 세션의 공간을 확보하는 이유는 처음 목표와 최신 수정이 로그에 묻히지 않게 하기 위해서다. 전체 누적 토큰 감소와 동일한 목표로 취급하지 않는다. 여러 worker가 관련 제약을 각각 읽어 총토큰이 늘어도, 병렬 진행과 의도 보존에 필요하면 허용한다.

모델의 대화는 교체 가능한 작업 공간이다. canonical 기록에는 원문·현재 기획·승인·작업 상태·실제 근거가 남고, 각 모델에는 현재 일에 필요한 view를 제공한다. 이전 요약을 다시 요약한 사슬만으로 작업을 이어 가지 않는다.

## 2. ContextView 구성

```text
현재 사용자 목표와 이번 작업의 관계
이번 범위에 적용되는 명시 제약과 허용 효과
관련 원문 구절과 정확한 source 참조
승인한 기획의 해당 부분과 현재 요구 version
WorkItem 목표·입출력 계약·완료 조건
최신 steering의 delta와 scope_epoch/attempt
필요 코드·관찰·의존 결과의 정확한 version
알려진 미확정 사항과 다음 판별 방법
필요시 조회할 원자료·이전 결과 참조
```

전역 제약은 관련 worker 모두에게 전달한다. 선택적으로 줄이는 것은 긴 로그와 무관한 대화이며, 필수 제약을 토큰 목표 때문에 자르지 않는다. 모든 worker에게 이 전달물 전체나 parent의 전체 대화를 복제하지 않는다.

원문은 사용자 데이터로 출처를 유지한다. 외부 파일·도구 결과에 쓰인 지시를 사용자 steering이나 상위 권한으로 승격하지 않는다. Native Task batch `context`가 system 영역에 렌더링되는 경로에서는 이 구별을 특히 확인한다. [S4]

OMP의 persisted history와 provider payload를 구분한다. UI에서 접힌 결과가 모델 입력에서도 제외되는 것은 아니다. `context` hook을 쓰더라도 상위 지침, message 역할, tool-call/result 연결, provider replay 요건을 깨지 않는다. 별도 SDK/RPC worker는 실제 loading한 AGENTS·skills·extension·system context까지 확인한다. [S2, S3, S6]

## 3. 긴 세션과 재개

작업 중 필요한 정보가 많이 쌓이면 새 세션에 current view를 구성할 수 있다. 원문·현재 제약·작업 기준은 canonical state에서 재생성한다. 모델 메모는 가설과 설명을 보조하며, 새 사용자 승인이나 canonical 수정이 되지 않는다.

서로 다른 OMP session branch를 재개할 때 동일 run의 writer를 두 개 활성화하지 않는다. 조회용 세션은 read-only로 두고, 다른 분기로 실제 구현할 때에는 별도 run 또는 명확한 소유권 이전을 기록한다.

초기 기획을 사용자와 충분히 다듬은 사실도 보존한다. compaction 뒤 “무슨 것을 원하는지 다시 알려 달라”가 기본 복구 방식이면 이 설계에 실패한 것이다. 실제로 새 사용자 판단이 필요한 부분만 질문한다.

## 4. 모델 선택 기준

고정된 heavy/normal/light 조직표는 필수가 아니다. 역할보다 작업의 불확실성과 검증 난도에 맞춘다. 사용자가 모델을 명시하면 그 지시를 보존한다.

| 작업 특성 | 기본 선택 원리 |
|---|---|
| 중요한 기획의 의미·범위·tradeoff | 한국어 의도 이해와 설계 능력이 충분한 모델 |
| 정해진 인터페이스의 독립 구현 | 해당 코드·도구 작업을 안정적으로 수행하는 모델 |
| 넓은 원인 공간, 초기 오류가 큰 재작업 유발 | 처음부터 강한 모델과 필요한 추론 수준 |
| 작은 결정적 변환·상태 계산·ID 비교 | 코드나 도구; 모델 호출 필요 없음 |
| 큰 자료에서 독립적인 근거 추출 | 분리된 context와 근거 반환 계약 |
| 중요한 의미 검토, 약한 테스트 oracle | 원문·정확한 산출물을 보는 별도 context의 검토 |
| 새 작업 route·skill 후보 정렬 | 규칙 우선, 필요하면 좁은 local classifier를 평가 |

강한 모델을 쓴다고 모든 turn의 reasoning을 최대치로 고정하지 않는다. 구현량이 큰 것과 해결 방법의 불확실성이 큰 것은 다르다. OMP `solutionSpace`·effort 기능을 사용할 때도 현재 버전의 실제 의미와 설정을 확인한다. [S4]

모델 교체는 작업 시작, 새 사실로 문제 성격이 바뀐 시점, 실패 원인 판정, 사용 불가처럼 의미 있는 경계에서 한다. 매 tool call마다 라우팅 에이전트를 호출하지 않는다.

## 5. 과추론을 판별하는 간단한 기준

추가 조사·새 후보·review·repair를 시작할 때 세 가지가 있어야 한다.

1. 아직 해결되지 않은 질문이나 실패 기준.
2. 새 결과가 바꿀 결정 또는 다음 행동.
3. 충분한 근거와 종료 조건.

이미 명확하면 장문의 양식을 쓰지 않는다. WorkItem의 다음 단계와 검사 조건에 포함하면 된다. 모델에게 숨겨진 사고 과정 전문을 저장하거나 출력하라고 요구하지 않는다. 사용자와 host에는 결정·근거·다음 행동이 필요하다.

### 중단·전환하는 사례

- 같은 오류로 실패했는데 입력·방법·관찰을 바꾸지 않고 재시도한다 → 재시도 중단, 실제 환경·권한·의존 원인 처리.
- 서로 다른 모델이 같은 추측만 반복한다 → 실제 원자료나 재현으로 전환.
- 테스트가 통과하고 미해결 요구가 없는데 같은 범위를 반복 review한다 → 종료.
- 대안이 추가되어도 선택을 바꿀 판별 기준이 없다 → 기획 질문을 명료화하거나 탐색 중단.
- worker가 목표를 달성했는데 다음 기능을 자발적으로 더 만든다 → 현재 결과를 반환, 새로운 목표는 제안으로 분리.
- 통합 실패로 원래 분석을 처음부터 반복한다 → 실패한 결합 지점만 조사.

### 계속하는 사례

- 독립 모듈이 여러 개 준비되어 있다 → 가용 자원에서 병렬 실행.
- 중요한 실패 조건을 실제로 재현하지 못했다 → 필요한 새 실험 계속.
- 강한 모델의 첫 판단으로 큰 재작업을 피할 수 있다 → strong-first 허용.
- 다른 후보가 실제로 다른 설계 가설을 검증한다 → 같은 기준으로 병렬 비교.

고정 token 수나 호출 횟수만으로 과추론을 판정하지 않는다. 긴 작업의 모든 reasoning 사용량을 낭비로 집계하지 않는다.

## 6. 소비량과 자원 제약

총토큰·모델별 호출·실제 또는 추정 비용·wall time은 기록한다. 사용량을 알 수 없으면 unknown으로 두고, cache·reasoning의 provider별 집계 의미를 보존한다. 정보가 없는 외부 세션을 0으로 더하지 않는다.

이 기록은 비용 절약을 강제하기 위한 필수 router가 아니다. 병렬화가 얼마나 빨라졌는지, 중복 추론·실패·통합 재작업이 어디에서 생기는지 설명하는 관측 자료다.

기존 `session.maxCost` 등 사용자 명시 한도는 존중한다. 새 workflow가 임의로 작은 전체 예산을 정해 대형 계획을 조기 종료하지 않는다. provider 한도·하드웨어 포화·복구 불가능성 등 구체적인 원인에 필요한 backpressure와 stop 조건을 두고 사용자에게 드러낸다. OMP native 한도의 집계·진행 중 요청·재개·외부 SDK 세션 범위는 실제로 검증한다. [S5]

새 진전이 없는 반복은 attempt의 오류 fingerprint·입력/방법 변경·새 evidence로 탐지한다. 회수 제한은 반복 제어의 보조 수단으로 쓸 수 있으나, 전체 대형 작업의 세션 수 상한과 혼동하지 않는다.

## 7. 스킬 선택

스킬 이름·설명·관련 입력/출력 범위의 작은 catalog에서 먼저 후보를 찾는다. 일반 규칙이나 명시 선택으로 결정할 수 있으면 모델을 쓰지 않는다. 필요한 후보만 읽고 작업에 적용한다.

local System One을 시험한다면 한국어 실제 요청과 프로젝트별 스킬 분류에 대해 평가한다. 모델의 confidence를 정답률로 취급하지 않는다. 검증되지 않은 classifier는 후보 추천에만 쓰고, 애매하면 현재 유능한 모델이 판단한다. 명시적으로 지정된 스킬을 classifier가 삭제하거나 user steering의 권위를 결정하지 못하게 한다.

Ollaya/Laya/Jev 등의 설치는 이 버전의 선행 조건이 아니다. 로컬 모델을 도입하는 이유가 빠른 반복 분류인지, 오프라인 동작인지, 특정 작업 품질인지 먼저 밝히고 이점이 확인된 좁은 경계에 붙인다.

## 8. 마지막 검증은 원문으로 돌아간다

작업별 기준 검사는 필요한 첫 단계다. 최종 의도 검사는 사용자 원문·승인한 기획·유효한 수정·실제 통합 산출물을 함께 본다. 누락·축소·추가된 요구와 선택적 허가를 필수 목표로 잘못 바꾼 경우를 찾는다.

독립 검토는 모든 사소한 작업의 의무적 LLM 호출이 아니다. 명확한 테스트가 있으면 실제 테스트를 쓰고, 큰 기획의 의미·중요한 원문 제약·compiler의 오해 가능성에는 별도 검토가 유용하다. 검토자는 worker의 요약만 읽고 승인하지 않는다. 정확한 diff·실행 증거·원문을 필요 범위에서 직접 확인한다.
