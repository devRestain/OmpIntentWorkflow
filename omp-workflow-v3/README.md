# OMP 작업 환경 v3 — 대화로 기획하고, 최신 의도로 병렬 구현하기

작성일: 2026-11-10 (Asia/Seoul)

이 묶음은 이전 v1·v2의 구현 지시를 대체한다. 실제 로컬 환경에 설치한 프로그램이 아니라, OMP가 환경을 조사하고 구현할 때 사용할 실행 프롬프트·설계·검증 자료다.

## 최종 목표

사용자는 원하는 결과를 자연어로 탐색하고, 마음에 드는 기획이 될 때까지 대화로 수정한다. 확정한 기획은 여러 모델이 실제 Git linked worktree에서 병렬로 구현한다. 사용자는 실행 중에도 자유롭게 방향을 바꾸고, 변경이 어느 작업에 전달되어 어디까지 반영됐는지 확인한다. 모델의 기억과 문맥 길이에 작업의 연속성을 맡기지 않는다.

유지하는 세 철학을 다음처럼 구체화한다.

1. **규격화된 프롬프트 강화 자동화:** 자연어 → 출처가 있는 의도 → 대화로 다듬은 기획 → 승인된 실행 조건으로 연결한다. 좋은 방법을 제안하되 목표를 몰래 바꾸지 않는다.
2. **다중 모델과 컨텍스트 분리로 의도 보존:** 원문·유효한 수정·현재 기획·실행 근거를 외부 상태로 유지하고, 각 작업자에게 최신의 관련 부분을 전달한다. 수신과 실제 반영을 구별한다.
3. **과추론 억제:** 새 증거나 달라질 결정이 없는 재분석·반복 검토·무의미한 재시도를 줄인다. 유용한 병렬 세션·높은 총토큰·강한 모델을 그 자체로 억제하지 않는다.

## v2에서 명시적으로 바뀐 결정

| v2의 기본값 | v3의 기본값 |
|---|---|
| 불확실성을 조사한 뒤 가능한 실행을 바로 진행 | 새 목표는 대화형 기획부터 시작하고, 사용자가 확정한 버전에서 구현 시작 |
| 전체 토큰·비용 감소가 주요 최적화 대상 | 올바른 결과까지의 시간과 사용자 통제력이 우선; 소비량은 관측값 |
| 보수적인 호출·시간·동시성 상한을 새로 강제 | 기존 명시 한도는 존중하되, 새 비용 절약 상한은 강제하지 않음 |
| 우선 동기 Task 경로를 완성 | 사용자 입력이 살아 있는 비동기 병렬 실행이 필수 |
| native Task와 얇은 extension을 가정 | OMP 재사용 + 응집된 workflow 확장 + 필요한 linked-worktree 세션 어댑터 |
| revision 불일치 결과를 재검토 | 전체 revision과 작업별 영향 버전을 구별해 무관한 작업을 살림 |
| 부분 의도 수정 | 수신·영속화·전달·확인·실제 반영을 추적하는 제어 절차 |

전역 비용 한도가 이미 설정되어 있으면 삭제하지 않는다. 기획에서 충돌을 드러내고 사용자가 정한 정책을 적용한다. OOM·provider rate limit·디스크·공유 테스트 환경의 제한은 비용 절약과 다른 실행 제약이다.

## OMP에 전달하는 법

1. 이 디렉터리를 로컬에 둔다. 합본 `OMP_SETUP_HANDOFF.md`만 전달해도 된다.
2. `BOOTSTRAP_PROMPT.md`를 첫 지시로 사용한다. OMP는 먼저 실제 설치 환경과 기존 설정을 읽고, 구체적인 구현 기획을 보여 준다.
3. 기획을 대화로 고친다. 원하는 버전이 되면 “이 기획으로 구현 시작”이라고 말한다.
4. OMP가 구현·검증·사용법·복구 절차를 완성한다. 설계 문서를 다시 쓰는 것만으로 설치 완료라고 보고하지 않는다.

자연어 입력이 기본 인터페이스다. 구현에서 보조 명령을 제공하더라도 사용자가 매번 구조화 형식이나 revision 번호를 외워야 해서는 안 된다.

## 구현 선택

현재 추천은 **OMP 기반**이다. OMP의 모델 연결·도구·세션·기획 UI 등을 재사용하고, 이 사용자의 고유 요구인 목표 버전·스티어링 전달·실제 worktree 배정·오래된 결과의 통합 차단을 한 workflow package에 구현한다.

`isolated: true`가 실제 Git linked worktree임을 가정하지 않는다. 설치 버전의 기능이 요구를 충족하지 않으면, `git worktree add`로 만든 경로에서 OMP SDK/RPC 세션을 실행하는 좁은 어댑터를 사용한다. 나중에 AgentFabric이 실행 상태를 소유하면 같은 의미 규칙을 pi 어댑터로 옮길 수 있게 한다.

## 보장 범위

“의도가 항상 적시에 전달”된다는 바람은 다음처럼 검증 가능한 조건으로 구현한다: 유효한 입력이 보존되고, 관련 작업의 다음 제어 가능한 행동 전에 새 지시가 확인되며, 오래된 결과는 최신 기준으로 검증하지 않으면 채택되지 않는다. 실행 중인 비중단 도구의 과거 부작용을 되돌리거나 모델의 의미 해석이 항상 옳음을 보장한다고 쓰지 않는다.

초기 계획의 확정은 사용자가 요구한 제품 동작이다. 실행 중 명백한 수정, 이미 승인한 범위의 방법 개선, 오류 복구마다 불필요하게 재승인을 요구하지 않는다.
