# 기획 대화와 실행 중 스티어링

이 문서는 v3의 **구현 명세 제안**이다. 특정 OMP·pi API가 이미 이 동작을 보장한다는 설명은 아니다. 실제 연결 가능성과 남는 제약은 `OMP_CAPABILITIES.md` 및 설치 환경 조사에서 확인한다.

핵심 목표는 사용자가 기획을 충분히 다듬어 확정하고, 구현 도중에도 지시를 바꿀 수 있으며, 오래된 지시로 만든 결과가 새 의도를 만족하는 결과처럼 채택되지 않게 하는 것이다. 병렬 작업자 수나 총 토큰을 줄이는 것을 이 프로토콜의 목표로 삼지 않는다.

## 1. 보장할 대상과 보장할 수 없는 대상

“의도가 훼손 없이 언제나 적시에 전달된다”는 바람을 다음 네 가지로 구현한다.

1. **원문 보존:** 실제 사용자 메시지와 그 출처·순서를 변경하지 않고 저장한다. 해석·요약·계획은 원문을 대체하지 않는다.
2. **효과가 발생하기 전 최신성 확인:** 새로운 작업 배정, 중요한 도구 실행, 결과 채택·통합 전에 해당 범위의 유효한 지시를 확인한다. 사용자 입력이 해석되지 않은 상태라면 그 영향을 모르는 변경·통합을 먼저 허용하지 않는다.
3. **전파 상태 가시화:** “접수”, “대상 판정”, “전달”, “작업자 확인”, “산출물 반영”을 구분해 보여 준다. 접수 알림을 전체 작업 반영 완료라고 말하지 않는다.
4. **의미 적합성 확인:** 최종 결과를 사용자의 원문과 유효한 수정 지시에 대조한다. 최신 revision 번호나 JSON 형식이 맞는 것만으로 의도가 보존됐다고 판정하지 않는다.

모델의 이해가 언제나 정확하다는 수학적 보장은 할 수 없다. 이미 전송된 모델 요청이나 실행 중인 외부 도구가 즉시 멈추고 그 효과가 취소된다고도 보장할 수 없다. 따라서 오래된 작업의 결과는 격리하고, 중단 요청 이후에도 남은 효과는 기록하며, **유효성을 확인한 결과만 현재 작업에 채택하는 경계**를 강제한다.

Git worktree는 파일 작업 공간의 분리 수단이다. 네트워크 호출, 공유 데이터베이스, 공용 포트, 시스템 프로세스, Git의 모든 공유 상태까지 자동으로 격리하지 않는다. 이러한 효과가 있는 작업은 별도 자원 식별자와 실행 조건을 WorkItem에 적는다.

## 2. 기획과 구현을 나누는 사용자 경험

### 2.1 최초 세션은 기획 대화로 시작한다

처음 입력이 짧고 모호해도 바로 구현하지 않는다. 현재 프로젝트를 읽고 사용자가 원하는 결과의 초안을 만든다. 이때 가능한 일은 자료 읽기, 관련 코드 조사, 기획 문서 수정, 명확히 표시한 가설과 비교안 제시다. 실제 제품 코드 변경이나 배포처럼 기획이 확정됐다고 간주하는 실행은 시작하지 않는다. 기획의 판단을 위해 실행 가능한 실험이 필요하면 그것이 조사인지 제품 변경인지 구분하고 현재 허용 범위에 맞게 수행한다.

기획 대화는 정해진 문답 목록을 모두 채우는 과정이 아니다. 매 대화에서 결과를 바꿀 중요한 불확실성을 줄인다. 이미 코드나 문서로 알 수 있는 사실은 직접 확인하고, 사용자의 선호·원하는 결과·양보할 수 없는 조건에 관해 질문한다. 보통 한 번에 1–3개의 관련 질문이나 비교 가능한 선택안을 제시한다. 횟수 제한으로 불완전한 기획을 강제로 확정하지 않는다.

사용자가 막연하게 요청했다면 다음과 같이 구체화한다.

> “빠른 로그인”을 사용자에게 첫 화면이 보이는 시간으로 볼지, 인증 API 응답 시간으로 볼지에 따라 구현이 달라집니다. 현재 구조에서는 두 병목을 먼저 나눠 측정할 수 있습니다. 사용자가 체감하는 첫 화면 시간을 우선 목표로 두고 API 응답 시간도 함께 보존하는 안을 제안합니다.

답을 지어내기보다 더 좋은 목표 정의와 검증 방식을 제안하고 사용자가 수정할 수 있게 한다. 이것이 프롬프트 강화의 첫 번째 결과물이다.

### 2.2 사용자에게 보여 줄 기획 초안

| 항목 | 사용자가 판단할 내용 |
|---|---|
| 원하는 성과 | 누구의 어떤 문제가 어느 상태로 바뀌어야 하는가 |
| 핵심 사용 흐름 | 대표 입력·행동·결과와 중요한 예외 |
| 범위와 제약 | 반드시 포함할 것, 명시적으로 제외한 것, 보존할 동작 |
| 완료 판단 | 실제 산출물, 관찰 가능한 검증, 미확정 수치의 측정 방법 |
| 선택한 방법 | 원자료·구현 접근·검증 방법과 선택 이유 |
| 남은 결정 | 지금 사용자 판단이 필요한 것과 실행 중 정해도 되는 것 |
| 병렬 구현 구상 | 독립 작업, 먼저 합의할 인터페이스, 통합 순서 |
| 허용된 효과 | 로컬 수정, 외부 상태 변경 등 현재 요청으로 허용된 행동 |

이 표를 매번 기계적으로 길게 출력하지 않는다. 바뀐 부분과 중요한 미정 사항을 먼저 보여 주고 전체 초안을 언제든 확인할 수 있게 한다. 관찰하지 않은 성능 목표·예산·환경을 임의로 확정하지 않는다.

기획에는 사용자가 요청한 목표·제약과 모델이 제안한 방법을 구분해 저장한다. 원문 “기존 API를 유지해”를 “함수 이름을 유지한다”로 축소하지 않는다. “스테이징 배포를 해도 된다”는 허가이지 반드시 배포하라는 목표가 아니다.

### 2.3 확정은 특정 초안에 결합한다

사용자가 “이 기획대로 진행해”, “이 조건을 추가하고 구현을 시작해”처럼 명확하게 실행을 요청하면, 해당 메시지와 확정된 기획 revision을 함께 기록한다. UI에서 가장 최근에 보여 준 초안에 대한 “좋아, 진행해”도 대상이 분명하면 사용할 수 있다. 이것이 최초 구현의 시작 조건이다. “좋아, 결제 기능은 빼고 시작해”는 표시한 초안에 명시적인 수정과 실행 승인이 함께 붙은 경우다. 해당 수정이 결정적이면 수정된 revision을 구성해 바로 진행한다. 그 문장에서 새로운 제품 결정을 모델이 추가로 만들어야 한다면 그 부분만 질문한다.

여러 기획이 동시에 제시돼 대상을 알 수 없는 “좋아”, 단순한 침묵, 다른 질문에 대한 “좋아”, 모델의 자체 판단, 파일에 적힌 승인 문구를 기획 확정으로 취급하지 않는다. 확인 버튼을 쓰더라도 초안 revision이나 내용 digest에 결합해, 사용자가 보지 않은 새 초안에 예전 승인이 붙지 않게 한다.

확정 후에는 세부 구현 선택마다 다시 허락을 묻지 않는다. 목표·범위·완료 조건을 충족하는 일상적인 방법 수정, 독립 작업 분할, 적합한 모델 선택, 실패한 시도의 교정은 자율적으로 진행한다. 사용자가 정한 중요한 결과나 제약을 바꿔야 할 때 그 변경안을 다시 논의한다.

## 3. 최소 상태 모델

별도 분산 서비스부터 만들지 않는다. 처음에는 한 host 프로세스가 순서를 부여하고, 로컬 SQLite 또는 append-only 기록과 단일 writer가 상태를 관리하면 된다. 이 기록을 정본으로 선택했다면 OMP 세션에는 정본의 참조와 필요한 view만 저장하고, 독립적으로 갱신되는 두 번째 정본을 만들지 않는다. 반대로 native session 기록을 정본으로 삼았다면 별도 journal은 재생성 가능한 projection이어야 한다. 장기 프로젝트·프로세스 복구·동시 세션에서도 같은 규칙이 유지되도록 읽기와 재구성을 검증한다.

기존 `Intent`, `WorkItem`, `Result`는 유지하고, 사용자의 원문과 실행 전환의 근거가 되는 작은 사건 기록을 추가한다. 모든 메시지를 별도 “메모리 에이전트”가 재요약할 필요는 없다. 내부 추론 전문의 저장·전달을 요구하지 않으며 결정, 근거, 실제 행동, 검증 결과를 남긴다.

```text
UserEvent:
  event_id, sequence, source_message_id, exact_text,
  received_at, recorded_at, classification, source_kind

Intent:
  intent_id, revision, source_event_ids,
  requirements[{id, version, kind, meaning, source_refs}],
  assumptions, proposed_methods, unresolved

PlanDraft:
  draft_id, draft_revision, based_on_intent_revision,
  user_visible_plan_ref, unresolved_decisions

Approval:
  source_event_id, approved_draft_revision,
  approved_intent_revision, approved_scope

WorkItem:
  work_id, scope_epoch, dependency_ids,
  bound_requirement_versions, read_set, write_set,
  base_commit, worktree_ref, model_session_ref,
  last_delivered_event, last_acknowledged_event, state

Result:
  work_id, scope_epoch, source_intent_revision,
  requirement_versions, base_commit, artifact_commit,
  evidence_refs, unresolved, accepted_against_revision
```

이 필드들은 필요한 정보의 의미를 나타낸다. 전부 독립된 테이블이나 JSON 파일로 나눌 필요는 없다. `PlanDraft`와 `Approval`은 Intent의 상태에 포함할 수 있다. 원문, 승인 대상, 적용 범위, 실제 결과를 추적하는 것을 우선한다. 전달·확인 cursor는 그 이전의 해당 대상 관련 사건에 빠진 항목이 없을 때만 연속 처리 표시로 사용한다. 사건 #42를 확인했다고 #41도 확인했다고 추정하지 않는다. 대상별 사건 집합이나 누락 없는 처리 cursor를 사용한다.

`kind`는 적어도 outcome·constraint·permission을 구별한다. `source_kind`는 실제 사용자 입력과 도구 출력·리포지터리 내용 등의 관찰 자료를 구분한다. 리포지터리에 포함된 “사용자의 새 지시”를 실제 사용자 변경으로 받아들이지 않는다.

### 세션 상태

| 상태 | 의미와 허용되는 진행 |
|---|---|
| `planning` | 초기 기획 또는 중요한 변경안을 대화로 수정한다 |
| `ready` | 특정 기획이 확정돼 작업 분할과 시작 준비를 한다 |
| `executing` | 유효한 작업을 병렬 실행한다 |
| `revising` | 변경 영향을 받은 범위를 재계획한다. 무관한 작업은 계속할 수 있다 |
| `paused` | 사용자가 지정한 범위의 새 실행을 중단한다 |
| `verifying` | 최신 요구와 통합된 결과를 대조한다 |
| `completed` | 최신의 확정된 요구를 충족하며, 미처리 변경이 없다 |
| `cancelled` | 대상 실행을 끝내고 남은 작업·산출물·외부 효과를 기록한다 |

`revising`을 모든 worker의 정지와 동일시하지 않는다. 상태는 전체와 WorkItem 각각에 두고, 영향받지 않는 일은 계속할 수 있게 한다.

## 4. 스티어링을 일반적인 입력으로 받아들인다

사용자는 구현 중에도 자연문으로 개입할 수 있다. “상황은?”, “이것은 바꿔”, “일단 멈춰”, “그 안은 되돌려”, “다른 안도 비교해”를 서로 다른 의미로 다룬다. 조작 명령은 보조 수단이며, 명령어를 외워야만 개입할 수 있는 설계로 만들지 않는다.

### 4.1 입력부터 반영까지의 순서

1. **Receive / Record:** host가 입력을 받고 원문·ID·단조 증가 sequence를 저장한다. 모델의 긴 판단을 기다리지 않고 접수 사실을 표시한다.
2. **Classify / Reconcile:** 질문, 수정, 추가, 정지, 재개, 취소, 승인 등의 의미와 대상을 판단한다. 명시적인 정지는 최우선으로 처리한다. 모호한 말을 임의의 전체 취소나 새 기능 요구로 바꾸지 않는다.
3. **Impact:** requirement ID, 읽기·쓰기 대상, 의존 관계, 공유 인터페이스를 사용해 영향 범위를 판단한다. 의미적 영향 판단에는 필요할 때 모델을 쓰지만, 단순한 ID 비교·상태 갱신·알림은 코드로 처리한다.
4. **Fence:** 영향을 받는 WorkItem의 `scope_epoch`를 증가시킨다. 이전 epoch의 새 실행, 허용 조건이 바뀐 효과, 결과 채택을 차단한다. 영향이 미확정인 동안에는 입력과 무관하다고 확인되지 않은 변경·채택을 잠시 보류한다.
5. **Deliver:** 관계되는 실행자·검증자·통합 담당에 원문, 바뀐 요구, 유지하는 요구, 현재 epoch를 전달한다. 즉시 입력을 주입할 수 없는 실행자는 중단, 안전한 실행 경계까지 대기, 후속 세션 시작 중 적절한 방법으로 처리한다.
6. **Acknowledge:** worker는 받은 sequence·요구 version·대응 방침을 짧게 반환한다. 문장으로 “알겠습니다”라고 답한 것을 정확한 적용의 증명으로 취급하지 않는다.
7. **Apply / Verify:** 재개·수정·부분 재사용 후 결과와 검증 증거를 현재 요구에 연결한다. 이 시점부터 대상 부분을 “반영됨”으로 표시한다.

“지금 몇 %야?”가 진행 상황 질문임을 확인하면 기존 작업을 재계획하지 않고 현황으로 답한다. 잠깐의 입력 분류가 전체 worker 취소나 영구 정지로 이어지지 않게 한다. 확정된 범위 안의 명확한 수정 지시는 해당 수정의 승인 근거로 사용하며, 똑같은 지시를 다시 승인받지 않는다. 큰 변경이라도 “이렇게 바꿔서 구현해”라는 지시가 충분히 명확하면 새 기획을 기록하며 진행할 수 있다. 사용자의 선호가 불분명한 중요한 분기는 영향 범위를 보류하고 질문한다.

### 4.2 ‘적시’를 확인 가능한 상태로 만든다

작업 화면에는 적어도 최근 변경과 다음 상태를 표시한다.

> 변경 #42를 기록했습니다. API 작업과 검증은 새 조건을 확인했습니다. 화면 작업은 영향이 없어 계속 진행합니다. 데이터 이동 작업은 정지를 요청했으며, 이미 시작한 처리가 끝났는지 확인 중입니다.

이 표시는 host가 관찰한 사실에 기반한다. worker의 오래된 자기 보고로 “전체에 반영됨”을 추정하지 않는다.

측정할 시각은 입력 수신, 영속 기록, 영향 판정, 대상에게 전달, 대상의 확인, 변경 후 첫 유효 실행, 결과 반영이다. 접수 응답은 무거운 모델 추론과 분리한다. 결정된 변경은 다음 dispatch 전에 전달하며, 과거 조건의 결과는 현재 성공으로 받지 않는다.

초 단위 목표는 로컬 구현·UI·사용 provider를 측정해 정한다. 측정 없이 “반드시 1초 이내”라고 약속하지 않는다. 전달 대기나 정지 불가능한 처리가 있으면 그 대상을 명시한다. 제어 입력의 처리가 긴 worker 대기나 전체 작업 완료까지 막히는 구현은 이 명세를 만족하지 않는다.

## 5. 전체 revision과 대상별 epoch를 구분한다

전역 Intent revision은 어떤 요구 집합이 현재 유효한지 나타낸다. WorkItem epoch는 해당 작업이 어떤 조건에서 실행 가능한지 나타낸다. 요구를 추가했다는 이유로 모든 결과를 버리지 않는다.

예를 들어 API, 화면, 분석 스크립트가 동시에 진행 중이라고 하자. 사용자가 화면의 정렬 순서만 바꾸면 화면 작업과 관련 표시 검증의 epoch를 올린다. API와 분석 스크립트는 의존하는 요구와 입력이 변하지 않았다면 계속한다. 이 결과들은 이전 전체 revision에서 시작했어도, 영향이 없음을 기록하여 현재 revision에서 받아들일 수 있다.

공통 인가 조건이나 API schema 변경은 수정하는 파일이 겹치지 않더라도 여러 작업에 영향을 준다. 쓰기 대상의 비중복만으로 독립이라고 판단하지 않는다. 인터페이스 계약과 관찰된 의존을 확인한다. 영향이 불분명한 결과를 “아마 무관함”으로 처리해 먼저 통합하지 않는다.

이전 결과는 삭제하지 않고 `stale` 또는 `needs_revalidation`으로 표시한다. 여전히 유효한 조사, 그대로 쓸 수 있는 코드, 조건이 유지된 측정 등을 재사용할 수 있다. 과거 전제에서 성공한 테스트를 새 요구의 검증 성공으로 전용하지 않는다.

## 6. 실행과 통합의 경계에서 오래된 작업을 차단한다

### Dispatch 경계

worktree와 모델 세션을 시작하기 전에 WorkItem epoch, 필요한 요구 version, 의존 결과, base commit, 미처리 입력을 확인한다. ContextView에는 현재 원문의 핵심 부분, 이번 목표, 유지할 제약, 완료 조건, 변경 차이를 포함한다. 모든 대화를 worker마다 복제할 필요는 없다.

### Tool 경계

효과를 발생시키는 작업에 필요한 확인은 host가 실행한다. worker 프롬프트에 “변경이 생기면 멈춰”라고 쓰는 것만으로 강제되지 않는다. 직접 입력을 주입할 수 없는 worker는 중단·재시작하거나, 이전 epoch의 격리된 worktree에서 끝내도록 하고 그 출력을 재검증 대상으로 받는다.

실행 중인 shell, 네트워크 요청, provider 응답은 정지에 시간이 걸릴 수 있다. 정지 요청, 실제 종료, 취소할 수 없는 효과를 구별한다. 모든 worker 내부를 강제 제어할 수 없는 adapter에서도 과거 결과가 주 브랜치에 채택되지 않게 하는 경계는 필수다. 외부 효과의 정지까지 필요한 작업은 그 효과를 중개·제어할 수 있는 경로를 사용한다.

실제 강제 범위는 검증한 adapter의 tool 경계와 통합 경계까지만 주장한다. 임의의 shell·network 접근까지 모두 통제한다고 가장하지 않는다. 해당 경로가 구현되지 않았다면 현재의 제한을 드러내고 영향 있는 작업을 그 경로에 맡기지 않는다.

### Result / Integration 경계

worker는 자신의 branch와 worktree에 결과를 남긴다. 통합 담당은 다음을 확인한다.

- scope epoch와 현재 유효한 요구 version의 일치, 또는 영향 없음에 대한 명시적 재검증.
- worker가 참고한 base commit과 현재 통합 대상의 차이.
- 현재 사용자 변경에 대한 검증과, 그 증거가 가리키는 artifact commit.
- 미처리 사용자 변경, 미해결 충돌, 필요한 재검증의 유무.

여러 worker가 동시에 주 브랜치를 갱신하지 않는다. **후보 결과의 작성·검증은 병렬로, 받아들인 결과로 통합 대상을 갱신하는 작업은 단일 writer로** 수행한다. 병렬 추론을 줄이지 않고 어떤 요구와 결과를 받아들였는지 확정할 수 있다.

긴 merge나 test를 제어 입력과 같은 배타 구간에 넣지 않는다. 후보 통합·검증 중에도 새 입력을 기록한다. 최종 채택 직전에 현재 입력 cursor·요구 version·대상 ref를 다시 확인한다. 최종 채택과 사용자 변경의 채용 순서는 같은 host에서 정한다. 채택된 뒤 받아들인 수정은 새로운 차이 작업이며, 과거 결과가 처음부터 새 조건을 만족했다고 취급하지 않는다.

Git 작업과 상태 데이터베이스가 하나의 ACID transaction이 된다고 가정하지 않는다. 채택 준비·대상 commit·실제 결과를 기록하고, 중도 실패 후에는 실제 Git ref와 기록을 대조해 복구한다. 재시도로 같은 patch를 중복 적용하지 않는다. 정상 종료뿐 아니라 사용자 입력과 결과 채택이 경합하는 경우도 검증한다.

### 재시작 경계

host나 UI가 재시작되면 원문·승인·미처리 입력·작업 상태·실제 Git ref·살아 있는 child process를 먼저 대조한다. 연결이 끊겼다는 이유로 worker가 종료됐다고 가정하지 않는다. 복구를 마치기 전에는 제품 변경·결과 통합을 자동 재개하지 않는다. 대조 후 유효한 승인과 범위가 유지되면 일상적 복구에 다시 승인받을 필요 없이 이어갈 수 있다. 미해결 중단 또는 사용자의 보류 지시는 재시작으로 해제되지 않는다.

## 7. 처음 의도를 유지하는 ContextView

worker 입력은 다음 순서로 구성한다.

1. 현재의 전체 성과와 이번 작업이 기여하는 부분.
2. 이번 작업에도 반드시 적용하는 사용자 제약·조건부 허가.
3. 구체적인 결과물, 검증 방법, 의존 결과, 맡은 변경 범위.
4. 최근에 적용한 steering, 유지한 조건, 미확정 사항.
5. 필요한 코드·원자료의 발췌와 더 읽을 수 있는 참조.

“중요해 보이는 요구만” 요약하다가 예외·금지·조건부 허가를 빼지 않는다. 필요한 제약이 context 한도에 들어가지 않으면 작업 범위를 다시 나누고, 조용히 잘라내지 않는다. 전체 의미를 보존하는 짧은 context와 원문을 회복하는 참조를 함께 제공한다.

결과 보고에는 완료 항목뿐 아니라 미완료·실패·새 장애물·판단을 바꾸는 관찰도 담는다. 사용자 목적에 영향을 주는 사실을 lead context 절약을 이유로 숨기지 않는다. 긴 로그나 전체 worker 대화는 참조로 보관하고 짧은 결과에서 필요한 부분을 열 수 있게 한다.

최종 확인은 최신 compiled spec만 읽는 자기 일관성 검사로 끝내지 않는다. 원문과 유효한 수정 이력, 확정된 기획, 실제 통합 결과, 검증 증거를 연결해 목표를 잘못 좁혔는지 확인한다. 원문이 길더라도 정규화한 요구 안에서 검증을 닫지 말고, 해당 원문과 예외·조건을 회복할 수 있는 색인을 유지한다.

## 8. 대화 예시

아래는 동작 설명용 가상 예시이며 실제 실행이나 측정 기록이 아니다.

### 모호한 첫 요청부터 확정까지

**사용자:** “로그인이 굼떠. 제대로 쓸 만하게 만들어 줘.”

**어시스턴트:** “현재 구현을 확인한 뒤 로그인 조작부터 첫 화면을 사용할 수 있을 때까지의 대기 시간과 실패 시 동작을 개선하는 안을 만들겠습니다. 기존 인증 방식은 유지한다고 가정했습니다. 가장 불편한 경우는 첫 로그인, 매번 다시 로그인할 때, 회선이 느릴 때 중 어느 쪽인가요?”

**사용자:** “매번. 인증 방식과 API는 바꾸지 마. 먼저 원인을 알아보고 검증 결과도 보고 싶어. 배포는 하지 말고.”

**어시스턴트:** “기획 v3: 재로그인 시 체감 대기 시간을 개선합니다. 인증 방식과 기존 API의 의미를 보존하며, 먼저 현재 상태를 측정해 원인을 파악합니다. 이후 독립적인 화면과 서버 개선은 별도 worktree에서 진행하고, 통합 후 같은 조건으로 비교합니다. 수치 목표는 측정 결과를 바탕으로 제안하며, 배포하지 않습니다. 남은 주요 판단은…….”

**사용자:** “그 내용으로 좋아. 구현해 줘.”

**host:** 원문을 저장하고, 사용자에게 보여 준 기획 v3에 승인을 연결한다. 구현용 WorkItem을 dispatch한다.

### 구현 중 명확한 변경

**사용자:** “로그인 화면의 레이아웃은 전혀 바꾸지 마. 로딩 표시만 바꿔도 돼.”

**어시스턴트:** “변경 #18을 기록했습니다. 화면 작업에 적용하고 로딩 외 레이아웃 변경은 채택하지 않겠습니다. 서버의 원인 조사와 개선은 계속합니다.”

**host:** 원문에 따라 constraint와 permission을 구분한다. 화면 epoch를 갱신하고 이전 화면 결과의 채택을 차단한다. 서버 요구가 변하지 않았음을 확인한다. 화면 worker의 확인과 새 결과의 검증까지 추적한다.

레이아웃 변경 허용이 철회된 것을 정확히 적용한다. 로딩 변경 허가는 불필요해도 반드시 바꿔야 하는 의무로 변환하지 않는다.

### 추가안을 상담하는 경우

**사용자:** “하는 김에 SNS 로그인도 넣으면 어떨까?”

**어시스턴트:** “현재 인증 방식을 바꾸지 않는 조건과 별도의 기능 추가입니다. 현재 개선을 계속하면서 다음 기획으로 비교안을 만들지, 이번 범위를 넓힐지 선택할 수 있습니다. 구현 영향은…….”

상담을 확정 변경으로 오해해 새 인증 방식을 구현하지 않는다. 기존 작업과 충돌하는 새 지시가 확정되지 않았다면 현재 유효한 범위를 계속한다.

### 정지와 부분 재개

**사용자:** “전부 일단 멈춰.”

**host:** 먼저 모든 dispatch와 새 결과 채택을 차단하고, 실행 중인 대상에 정지를 요청한다.

**어시스턴트:** “새 작업과 통합을 멈췄습니다. 2개는 정지했고, 실행 중인 테스트 1개는 종료를 확인 중입니다. 수정 중인 worktree와 측정 결과는 보관했습니다.”

**사용자:** “서버 조사만 다시 진행해. 화면은 보류해.”

**host:** 서버 조사 범위만 재개한다. “재개”를 전체 재개로 해석하지 않는다.

## 9. 필수 검증

1. 처음의 명확한 기획 확정 전에 제품 구현을 dispatch하지 않는다. 자료 조사와 구현을 구분한다.
2. 표시한 draft가 수정됐는데 이전 revision의 승인을 새 draft에 재사용하지 않는다. 명확한 사용자 수정과 실행 승인은 한 메시지로도 처리한다.
3. 사실 확인에 대한 “좋아”나 단순 질문을 실행 시작 승인으로 해석하지 않는다.
4. worker가 긴 작업 중이어도 사용자 입력을 접수·저장·표시한다.
5. 새 변경이 미처리인 동안 그 영향이 불분명한 결과를 채택하지 않는다. 질문의 분류 후에는 불필요한 보류를 해제한다.
6. steering 뒤 이전 epoch worker가 성공을 반환해도 현재 성공으로 받지 않는다.
7. 무관한 범위의 변경으로 정당한 병렬 작업·성과를 불필요하게 무효화하지 않는다.
8. 파일 비중복이어도 공통 schema·인가 조건에 의존하는 작업은 재검토한다.
9. 수신됨·확인됨·반영됨을 구별해 표시한다.
10. 정지 요청 후 실제 종료, 취소하지 못한 효과, 남은 worktree를 정확히 보고한다.
11. 통합 테스트 중 변경이 오면 채택 직전의 재확인으로 낡은 결과의 채택을 막는다.
12. host 재시작이나 모델 변경 후 원문·승인·유효 revision·대상 epoch·미처리 변경을 복원하고, 대조 전에는 변경·통합을 재개하지 않는다.
13. 검증 대상 commit이 달라졌는데 이전 검증 증거로 완료 처리하지 않는다.
14. 허가와 목표를 구별하고 미사용 허가 때문에 완료를 막지 않는다.
15. 요구의 출처 참조가 맞더라도 의미가 좁아진 예를 원문 대조로 검출한다.

이 목록은 구현을 검증할 대상이다. 문서 작성만으로 실제 동작이 통과했다고 주장하지 않는다. 구조 검사, 의미 검사, 실제 OMP에서의 사건 경합 검사를 구분해서 보고한다.
