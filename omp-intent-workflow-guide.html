목표를 말하고 기획을 다듬은 뒤, 확인한 기획만 실행에 맡깁니다. 작업자는 실제 Git worktree에서 병렬로 일하고, 변경 지시·검증·최종 결과는 대화 맥락과 별개로 기록됩니다.

별도 서버 없음. OMP의 모델·인증·SDK·스킬·터미널 UI를 재사용합니다.

처음 시작하기

01 / 시작

전역 설치를 완료한 환경이라면 다시 설치할 필요가 없습니다. 작업할 저장소 또는 Git이 없는 상위 작업 디렉토리에서 새 OMP 세션을 여는 것으로 시작합니다.

  1. 대상 디렉토리에서 OMP를 엽니다

    bun이 PATH에서 실제 실행 파일로 찾아져야 합니다. 여러 저장소를 함께 다루는 상위 디렉토리도 가능합니다.

    셸에서 실행 · 경로 교체 필요
    cd /path/to/your-workspace
omp

    원본 상위 디렉토리에 .git을 만들지 않습니다. 내부 저장소마다 실제 worktree와 commit을 유지하고, Git 밖 소스는 별도 비공개 스냅샷으로 격리합니다. State·Vault·설치 런타임·캐시는 자동으로 복사하지 않으며, 추가 비버전 자료는 기획의 readPaths에 필요한 범위만 선언합니다. readPaths는 쓰기 권한이 아닙니다.

  2. 목표와 바꾸면 안 되는 것을 함께 말합니다

    최종 결과, API, 금지 사항, 검증 방식을 구체적으로 적습니다. 처음부터 확실하지 않아도 됩니다. 중요한 선택은 기획 단계에서 정리합니다.

    OMP 입력창 · 목표 예문
    현재 저장소에 value.ts를 만들고 named export
identity(n:number):number 하나를 제공하고 싶어.
모든 number를 변환 없이 그대로 반환해야 해.
0, -0, 1.25, NaN, Infinity, -Infinity를 Object.is로 검사하자.
기존 파일과 공개 API는 변경하지 말고 의존성 추가·배포도 하지 마.
이미 설치된 bun -e와 node:assert/strict로 검증할 계획을 세워 줘.
먼저 기획만 작성하고, 구현 승인은 별도로 입력하겠다.

    예문은 value.ts가 아직 없다는 전제로 사용하세요. 이미 있다면 기존 내용을 읽어 충돌 여부부터 기획에 반영하도록 요청하세요.

  3. 기획을 확인하고, 필요한 만큼 수정합니다

    미정 질문에 답하고, 요구 ID·쓰기 경로·모델·검증 명령이 의도와 맞는지 읽습니다. 기획 수정 자체는 구현 승인이 아닙니다.

    OMP 입력창 · 승인 없는 수정
    기획 수정: 별도 테스트 파일은 만들지 말고 bun -e 검사로 확인해.
다른 요구와 금지 조건은 유지해. 아직 구현하지 말고 수정 기획만 보여 줘.
    중요한 미정 질문이 없는가?모든 필수 결과에 담당 작업이 있는가?쓰기 경로가 필요한 범위뿐인가?검증 명령에 외부 효과가 없는가?

  4. 표시된 정확한 기획을 승인합니다

    읽은 기획의 digest를 직접 지정하는 방식이 가장 명확합니다. <표시된-digest>는 화면에 나온 실제 값으로 바꿉니다. 간단히 approve 또는 /workflow approve라고 입력하면 현재 표시된 기획을 승인합니다.

    OMP 입력창 · 자리표시자 교체 필요
    /workflow approve <표시된-digest>

    진행 상황은 /workflow status로 확인합니다. 완료 메시지의 결과 경로 · 저장소별 commit · 검증 원장을 보관하세요. workspace:…는 여러 commit을 묶은 manifest ID이지 Git commit이 아닙니다. 원래 checkout에 자동으로 덮어쓰지 않습니다.

새 목표로 분리하려면 /workflow new 뒤에 목표를 입력하거나 /workflow new 새 목표 내용을 사용하세요. 실행 중인 작업이나 미처리 입력이 있으면 전환이 거절될 수 있습니다. 기존 일을 먼저 정리하고 상태를 확인하세요.
기획 진행은 한 박스에서 갱신됩니다. 현재 단계와 짧은 작업 설명·파일 경로를 표시하며, 읽기마다 대화 메시지를 쌓지 않습니다. 내부 추론 원문을 노출하거나 요약용 모델을 추가 호출하지 않습니다. 기획 결과·오류·완료 보고는 별도 메시지로 남습니다.

기획을 읽는 법, 승인이 뜻하는 것

02 / 권한

기획은 단순한 할 일 목록이 아닙니다. 어느 사용자 입력에서 나온 요구인지, 무엇을 변경하고 어떤 명령으로 확인할지를 함께 보여 주는 실행 계약입니다.

요구 종류를 구분해야 “허용”이 “의무”로 바뀌지 않습니다
종류의미입력 예시
outcome반드시 얻어야 할 결과“add(a:number,b:number)를 제공해.”
constraint실행 내내 지켜야 하는 조건“기존 공개 API와 사용자 파일을 보존해.”
permission할 수 있는 일. 반드시 해야 하는 일은 아님“필요하다면 읽기 전용으로 조사해도 돼.”
exclusion실행하면 안 되는 범위“외부 설치·배포는 하지 마.”
acceptance완료를 판단하는 조건“정상·오류 입력을 실제 검사로 확인해.”

승인 전에 확인할 8가지

  • Revision + digest내가 읽은 수정본과 승인할 수정본이 같은가?
  • 원문 출처요구의 event 참조가 실제 요청을 가리키는가?
  • 가정과 제안모델의 가정이 내 요구나 허가로 둔갑하지 않았는가?
  • 미정 질문중요한 제품 선택이 실제로 해결됐는가?
  • 담당 작업과 의존성필수 결과·인수 조건이 작업에 배정됐는가?
  • 쓰기 경로와 독점 자원무관한 파일·포트·DB를 건드리지 않는가?
  • 작업별 모델과 역할명시한 모델이 지시문뿐 아니라 Model 항목에 있는가?
  • 검증 명령실제 실행 가능하며 허용한 로컬 효과만 발생하는가?
승인으로 허용하는 것
표시된 기획의 작업과 선언된 로컬 검증 명령입니다. “이 조건을 바꾸고 구현해”처럼 수정과 실행 승인이 명확히 함께 오면 수정 기획을 반영해 실행할 수 있습니다.
승인으로 자동 허용되지 않는 것
배포, 인증정보 변경, 파괴적 Git, 새로운 유료 서비스, 무관한 파일 변경과 임의 외부 효과입니다. 불명확한 중요한 범위는 승인으로 추정하지 않습니다.

초안에는 질문이나 미배정 결과가 있어도 됩니다. 그러나 실행 승인은 중요한 질문이 해소되고 필수 결과·인수 조건이 작업으로 연결된 기획에만 가능합니다.

명령어 사전

03 / 제어

아래 명령은 셸이 아니라 OMP 입력창에 입력합니다. 작업 ID는 /workflow status 또는 기획에서 확인하세요. W1·W2는 예시이며 실제 ID와 다를 수 있습니다.

9개 명령

/workflow status상태 조회
전체 상태, 승인 여부, 미처리 입력, 작업별 epoch·attempt·전달·확인 ID를 봅니다. 조회만으로 완료 작업을 다시 열지 않습니다.
/workflow plan [목표]현재 기획 표시 / 목표 기획
인수가 없으면 현재 revision·digest·요구·쓰기 경로·모델·검증 명령을 다시 표시합니다. 목표를 붙이면 해당 입력을 보존하고 기획합니다. 구현 승인은 아닙니다.
/workflow approve [digest 또는 revision]현재 표시본 승인
인수가 없으면 현재 표시된 기획을 승인합니다. 오래된 digest나 다른 revision은 거절합니다. 중요한 미정 질문이 있으면 먼저 해소하세요.
/workflow tell <ID> <지시>대상 지정 steering
예: /workflow tell W1 유한 소수도 더하도록 수정해. 다른 조건은 유지해. 대상과 실제 의존 소비자를 함께 고려하며 무관 작업을 일괄 재시작하지 않습니다.
/workflow pause [IDs]전체 / 선택 일시정지
인수가 없으면 전체, W1,W2 또는 W1 W2를 주면 해당 작업과 영향받는 의존 작업을 멈춥니다. 새 효과·채택부터 차단하고 실제 종료를 기다립니다.
/workflow resume [IDs]명시적 재개
승인 전에는 인수 없는 resume으로 보존된 입력의 기획을 재개합니다. run UUID를 넣지 마세요. 승인 후에는 현재 승인·상태를 대조해 작업을 재개하며, 선택 ID는 개별 작업 ID입니다. 전체 중지는 인수 없는 resume으로 해제합니다.
/workflow cancel [IDs]전체 / 선택 취소
실행·채택과 기획 세션을 중단하고 늦게 도착한 응답을 무효화합니다. 기록과 산출물은 삭제하지 않습니다. 재시작해도 자동 해제되지 않으며, 승인 전의 명시적 resume은 기획만 재개합니다.
/workflow recover미완료 기획 / unknown 작업 복구
승인 전에는 이전 기획 세션을 교체하고 보존된 미처리 목표를 다시 기획합니다. 실패한 제어 명령은 재실행하지 않습니다. pause/cancel은 유지하므로 이때는 resume을 사용하세요. 승인 후에는 Git ref·원장·프로세스를 대조하고 중복 실행 없이 unknown 작업을 복구합니다.
/workflow new [새 목표]별도 목표 시작
새 run으로 분리해 기획부터 시작합니다. 기존 입력이 남아 있으면 먼저 전체 cancel을 입력하세요. 중단이 확인된 뒤 new로 전환하며 이전 run의 미완료 원문은 보존됩니다.

일치하는 명령이 없습니다. “상태”, “정지”, “recover”처럼 다른 단어로 검색하세요.

자연어도 사용할 수 있습니다. “진행 상황”, “일단 멈춰”, “재개”, “취소”, “확정하고 시작” 같은 입력을 처리합니다. 대상이 중요한 지시는 tell과 정확한 작업 ID로 범위를 분명히 하는 편이 좋습니다.

실행 중 지시를 바꾸는 법

04 / 변경

메시지를 보냈다고 코드에 반영된 것은 아닙니다. 입력을 기록한 시점부터, 작업자가 확인하고 새 산출물이 검증되는 시점까지를 나누어 추적합니다.

접수원문·순서·출처를 영속 기록합니다.
전달현재 작업 시도에 필요한 event 집합을 제공합니다.
확인 · ACK작업자가 현재 epoch·attempt와 정확한 event ID들을 확인합니다.
검증 · 채택새 요구를 만족한 정확한 commit만 결과로 채택합니다.
OMP 입력창 · 실제 ID 확인 후 사용
/workflow tell W1 add는 유한 정수뿐 아니라 유한 소수도 더하게 수정해.
숫자 문자열 강제 변환은 금지하고 잘못된 입력은 TypeError로 처리해.
format과 slug, 기존 API 보존·무설치·무배포 조건은 유지해.
바뀌는 범위

W1과 실제 영향받는 의존 작업은 새 epoch로 재검증합니다. 이전 조건으로 만든 늦은 결과는 stale로 남고 채택되지 않습니다.

유지하는 범위

쓰기 경로·의존성이 분리된 무관 작업은 계속할 수 있습니다. 이미 채택된 무관 결과와 기존 pause/cancel 상태를 무조건 초기화하지 않습니다.

설명용 상태 출력 예시 · 실시간 상태 아님
W1: running epoch=2 attempt=1 전달=1,2,3,5 확인=1,2,3,5
epoch
변경·중단 등으로 기존 실행 권한이 무효화되는 세대를 구분합니다. 예전 세대의 결과는 최신 결과가 아닙니다.
attempt
작업 실행 시도를 식별합니다. 같은 작업 ID라도 이전 시도의 ACK·산출물을 새 시도에 재사용할 수 없습니다.
전달 / 확인
event ID의 정확한 집합입니다. 큰 ID 하나를 확인했다고 중간에 빠진 입력까지 확인한 것으로 보지 않습니다.
범위가 불명확하면 안전하게 보류합니다. “이건 다르게 해” 대신 무엇을 바꾸고 무엇을 유지할지 적으세요. 불명확한 입력은 미처리로 남아 영향이 불확실한 효과·통합을 막을 수 있습니다. 이어지는 설명으로 해당 입력의 의도를 명확히 하세요.

병렬 실행은 폴더 분리보다 강합니다

05 / 실행 경계

작업마다 실제 git worktree add로 연결된 작업 디렉터리와 브랜치를 만들고, 별도 OMP SDK 세션을 실행합니다. 일반 폴더나 네이티브 Task의 격리 옵션만으로 linked worktree라고 간주하지 않습니다.

  • 현재 요구·epoch·ACK
  • 제한된 읽기·쓰기 도구
  • 산출물·미충족·미실행 검사 보고

병렬로 실행할 조건

  • 선행 의존 작업이 준비됐습니다.
  • 파일·디렉터리 쓰기 소유권이 충돌하지 않습니다.
  • 동일 포트·DB·출력 폴더 같은 독점 자원을 두 작업이 점유하지 않습니다.
  • 네이티브 task.maxConcurrency 상한 안입니다.

읽기 전용 문서나 사용자 event를 독점 잠금으로 만들지 않습니다. 플러그인이 임의의 토큰 절약 배치 상한을 추가하지 않습니다.

어떻게 검증하고 통합하나

  • 작업 산출물과 정확한 commit을 연결합니다.
  • 승인된 argv 검사를 깨끗한 체크아웃에서 실행합니다.
  • 최신 입력·요구 버전·epoch·ACK를 다시 확인합니다.
  • 원본 의도와 실제 결과를 독립 검토한 뒤 전체 완료를 판단합니다.

하위 작업이 accepted여도 전체 목표가 completed인 것은 아닙니다. 검사 실패나 최종 검토 실패를 완료로 덮지 않습니다.

검증 명령은 스스로 완결되어야 합니다. 호스트는 산출물 생성 후 argv를 직접 실행합니다. stdin은 닫혀 있고 셸 확장도 없습니다. 작업자는 임의 셸 명령을 실행하거나 다른 검사에 stdin을 연결할 수 없습니다. 보호 파일 기준 해시·바이트는 기획 중 읽어 고정하고, 변경 뒤 새로 캡처하지 마세요. 작업별 검사도 최종 통합에서 다시 실행됩니다.
원래 checkout을 강제로 갱신하지 않습니다. staged·unstaged·untracked 사용자 변경은 private-index baseline으로 보존합니다. 최종 메시지의 실제 결과 worktree에서 코드를 확인하세요. 채택 ref가 바뀌었다는 사실만으로 원래 폴더의 파일도 바뀌었다고 해석하면 안 됩니다.

모델·추론 수준·스킬을 선택하기

06 / 라우팅

역할별 추론 수준을 정하고, 모델 선택은 표시된 작업에 기록합니다. 지정이 없으면 워크플로 세션 모델을 따르며, 별도 선호가 없을 때 보수적 기본값은 openai-codex/gpt-6.1-sol입니다.

모델을 바꾸려면

기획 또는 scoped steering으로 요청하고 표시된 Model 값을 확인하세요. 지시문에만 모델 이름이 있고 실제 작업 필드가 다른 것은 원하는 설정이 아닙니다.

주 세션의 네이티브 모델 선택기를 바꿔도 이미 승인된 작업자 모델이 자동으로 따라 바뀌지 않습니다. Terra는 명시적 선택용이며, 카탈로그에 있다는 사실만으로 품질 우위를 주장하지 않습니다.

스킬을 사용하려면

자연어로 필요한 스킬을 명시하거나 네이티브 /skill 선택 흐름을 사용하세요. SDK가 발견한 스킬 메타데이터를 유지하고, 명시 선택한 본문과 필요한 자료를 제한된 읽기로 전달합니다.

프로젝트 지침과 설정의 기준은 원래 저장소입니다. 선택적 로컬 판단 모델 설치는 필수가 아니며 승인·채택 권한을 저렴한 분류기의 confidence에 위임하지 않습니다.

대화 밖에 남는 상태와 안전한 복구

07 / 영속성

모델의 요약은 권한의 원본이 아닙니다. 원문과 변경 순서, 기획·승인, 시도·ACK, commit·검증·채택을 영속 원장에 보존하고 필요한 맥락만 세션에 투영합니다.

기본 상태 구조 · 실제 위치는 활성 OMP 프로필의 getAgentDir() 기준
~/.omp/agent/workflows/<repo-key>/
├── active.json                 현재 run 참조
└── runs/<run-id>/
    ├── intent.sqlite           원문·기획·승인·작업·검증 원장
    ├── sessions/               네이티브 SDK 세션 로그
    └── git/ 또는 workspace/    저장소별 worktree·정확한 결과 manifest·채택 상태

재시작했다면 이 순서로

  1. 같은 저장소·OMP 프로필에서 새 세션을 엽니다. 같은 run ID가 복원되는 것은 정상입니다.
  2. /workflow status로 기획·승인·미처리 입력을 확인합니다.
  3. 기획 미작성 상태가 paused/cancelled이면 인수 없는 /workflow resume으로 기존 목표의 기획만 재개합니다. 중지되지 않은 미완료 기획이나 unknown 실행 작업은 /workflow recover로 복구합니다.
  4. 새 목표로 바꾸려면 /workflow cancel 후 /workflow new [목표]를 입력합니다. 기존 원문은 남습니다. 기획이 표시되기 전 approve를 반복하지 마세요.

복구가 보장하지 않는 것

복구·재개는 새 구현 승인이 아닙니다. 기획을 읽고 정확한 표시본을 승인해야 구현합니다. 접수·기획 활동·오류 메시지를 구분하세요.

Git ref 갱신과 SQLite는 하나의 트랜잭션이 아닙니다. 살아 있거나 정체가 불명확한 프로세스를 “종료됨”으로 가정하지 않으며, 이미 시작된 외부 효과를 되돌리지 않습니다.

이전 버전에서 비-Git 루트의 approve가 Git rev-parse 오류로 실패했는데 승인 상태가 남아 있다면, 새 OMP 세션에서 /workflow recover로 준비·실행을 이어갈 수 있습니다. 기존 승인과 원문은 삭제하지 마세요.

pendingrunningpausedcancelledunknownfailedaccepted

위 표시는 개별 작업 상태입니다. 전체 워크플로에는 planning·executing·verifying·completed 등의 별도 상태가 있습니다. 모델 교체·실제 컨텍스트 압축·정확한 세션 재개는 구축 검증에서 확인했지만, 모든 미래 입력의 의미 해석이 완벽하다는 뜻은 아닙니다.

자동 수정에도 경계가 있습니다. 실패한 호스트 검사나 독립 검토는 승인된 담당 작업과 의존 작업만 다시 열 수 있습니다. 새 권한·요구를 발명하지 않습니다. 같은 코드·실패 증거나 같은 산출물·수정 범위를 반복하면 새 진전이 없는 자동 반복을 중단합니다.

독립 모듈 3개를 병렬로 만들기

문제 해결과 명확한 한계

11 / 판단

오류나 보류는 우회할 대상이 아니라 현재 권한과 상태를 확인할 신호입니다. 아래 순서로 원인을 좁히세요.

approve했는데 실행되지 않습니다

/workflow plan으로 현재 표시본을 다시 확인하세요. 중요한 질문, 필수 결과에 대한 미배정 작업, 오래된 digest, 미처리 입력이 있으면 먼저 해결합니다. pause/cancel 상태나 프로세스 복구가 필요한지도 status에서 확인하세요. 원인을 보지 않고 반복 승인하지 마세요.

작업자가 기획 내용을 놓친 것 같습니다

실제 작업 ID와 빠진 요구를 /workflow tell로 지정하고, 유지할 조건도 함께 적으세요. 전달과 ACK, 새 epoch의 검증된 commit을 구분해서 확인합니다. 메시지 접수만으로 코드 반영 완료라고 판단하지 마세요.

완료됐는데 원래 폴더에 새 코드가 없습니다

정상적인 전달 방식일 수 있습니다. 완료 메시지의 “실제 결과” worktree를 확인하세요. 원래 checkout을 강제로 덮어쓰지 않습니다. 검증된 commit과 원장을 보관하고, 원래 브랜치에 반영하는 작업은 사용자 변경을 고려해 별도로 결정하세요.

네이티브 /plan·/goal 또는 다른 편집기와 충돌합니다

플러그인은 네이티브 plan/goal/vibe/loop 모드 충돌을 알리며 임의로 바꾸지 않습니다. 모드를 먼저 정리한 뒤 새 세션에서 시작하세요. 다른 CustomEditor 소유자가 있으면 덮어쓰지 않고 충돌을 보고하므로, 어떤 확장을 사용할지 정리한 후 reload해야 합니다.

작업자에게 네이티브 포커스 전환으로 지시하고 싶습니다

이 작업자는 독립 SDK 세션이지만 네이티브 Agent Hub의 포커스 가능한 자식으로 등록된 것은 아닙니다. 주 워크플로 입력이나 /workflow tell <ID> <지시>를 사용하세요. 무관한 네이티브 자식에게 보낸 DM은 워크플로 steering이 아닙니다.

시작 오류·unknown 또는 이미 제어 중이라는 메시지가 보입니다

PATH에서 실제 Bun 실행 파일을 찾는지, 같은 저장소를 다른 컨트롤러가 제어하는지 확인하세요. 컴파일된 omp 바이너리는 TypeScript worker 인터프리터가 아닙니다. 프로세스가 살아 있는지 불명확하면 파일·잠금을 임의로 삭제하거나 중복 실행하지 말고 status와 recover 결과를 확인하세요.

현재 파일과 이전 commit을 어떻게 구분해서 읽나요?

작업자의 read는 현재 작업 트리 또는 발견된 스킬 자료를 읽습니다. 과거 바이트는 필수 commit 인수를 가진 별도 read_history로 읽으며 HEAD 또는 전체 commit ID를 사용합니다. 줄 일부를 보여도 전체 파일의 SHA256을 보고합니다. 사용자 셸 명령이 아니라 작업자 도구 계약입니다.

설계·검증으로 확인한 경계

  • 사용자 원문·명시 승인과 모델 제안 구분
  • 작업 소유 경로·실시간 허가·epoch·ACK 확인
  • 실패 검사·오래된 결과를 완료나 최신 결과로 오인하지 않음
  • 기존 staged·unstaged·untracked 변경 보존
  • 무관한 네이티브 설정·cmux 확장 보존 검증

보장하지 않는 것

  • OS 샌드박스 또는 악의적인 프로젝트의 안전한 실행
  • 모든 자연어 의도의 완벽한 의미 해석
  • 즉각적인 중단이나 이미 발생한 외부 효과의 취소
  • 일반적인 성능 우위·모델 품질 우위
  • ignored 파일 자동 포함 및 모든 Git 상태 지원
신뢰할 수 없는 코드와 검증 명령을 승인하지 마세요. 승인된 검사도 실제 프로세스입니다. sensitive 입력, submodule, sparse/unmerged checkout, 특수 파일과 안전하지 않은 링크는 명시적으로 거절할 수 있습니다. 인증정보를 원문·명령·가이드에 복사하지 말고 네이티브 인증을 사용하세요.
